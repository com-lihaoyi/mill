= Vaadin

Builds https://vaadin.com/flow[Vaadin Flow] web applications: the production
frontend build (`npm install` and a Vite bundle), a self-contained production
distribution, and Vaadin's development mode for `run`. It is the Mill counterpart
of the `prepare-frontend` and `build-frontend` goals of Vaadin's Maven and Gradle
plugins.

Mix `mill.contrib.vaadin.VaadinModule` into the module hosting the Vaadin
application:

.`build.mill`
[source,scala]
----
//| mvnDeps: ["com.lihaoyi::mill-contrib-vaadin:$MILL_VERSION"]
//| mill-jvm-version: 21
package build

import mill.*, javalib.*
import mill.contrib.vaadin.VaadinModule

object app extends JavaModule, VaadinModule {
  def mainClass = Some("com.example.Application")

  def bomMvnDeps = Seq(
    mvn"org.springframework.boot:spring-boot-dependencies:4.1.1",
    mvn"com.vaadin:vaadin-bom:25.3.0"
  )
  def mvnDeps = Seq(mvn"com.vaadin:vaadin-spring-boot-starter")

  // development mode only: used by `run`, left out of the production build
  def runMvnDeps = Seq(mvn"com.vaadin:vaadin-dev")
}
----

[source,console]
----
> mill app.runBackground        # starts the app in Vaadin's development mode
> mill app.vaadinBuildFrontend  # production frontend build into out/app/vaadinFrontendBuild.dest
> mill app.vaadinPackage        # production distribution into out/app/vaadinPackage.dest/dist
> out/app/vaadinPackage.dest/dist/run-prod.sh
----

A complete example is part of the
xref:javalib/web-examples.adoc#_vaadin_flow_example[Java web examples].

== Development and production

Development-only dependencies such as `com.vaadin:vaadin-dev` (the Vite dev
server integration, dev tools and Copilot) or Spring Boot devtools belong in
`runMvnDeps`. `run` and `runBackground` use them to start Vaadin's development
mode; `VaadinModule` points Vaadin at the module directory, the frontend
directory and a build folder, as Vaadin only recognizes Maven and Gradle
projects by itself.

The production frontend build and `vaadinPackage` use `vaadinProdRunClasspath`
instead: the runtime dependencies of `mvnDeps`, including runtime-scoped
transitive dependencies, plus `vaadinProdRunMvnDeps`, the production
counterpart of `runMvnDeps`. So the dev tooling is not shipped, and as the
frontend build scans this classpath, its frontend resources do not end up in
the production bundle either. The bundle is built for exactly the classpath
that is shipped.

Runtime-only dependencies of the production application, such as a JDBC
driver or a logging backend, go into `vaadinProdRunMvnDeps`. A runtime
dependency needed in both modes goes into both lists:

[source,scala]
----
def vaadinProdRunMvnDeps = Seq(mvn"org.postgresql:postgresql:42.7.7")
def runMvnDeps = super.runMvnDeps() ++ vaadinProdRunMvnDeps() ++
  Seq(mvn"com.vaadin:vaadin-dev")
----

`vaadinPackage` produces:

* `dist/app.jar`: application classes and resources
* `dist/lib/`: module dependency and third-party jars
* `dist/vaadin-frontend/`: the production frontend bundle (`META-INF/VAADIN`)
* `dist/run-prod.sh`: a launch script

== Configuration

`vaadinFrontendDir`:: Vaadin's frontend directory: frontend sources (themes,
stylesheets, TypeScript views) and the `generated` folder Vaadin writes into.
Defaults to `frontend` next to `src` and `resources` in Mill's layout, and to
Vaadin's convention `src/main/frontend` in a `MavenModule`. It is used by both
the production build and development mode.
`vaadinFrontendConfig`:: npm/Vite configuration files (`package.json`,
`vite.config.ts`, ...). They are inputs of the frontend build, so that changing
them rebuilds the bundle.
`vaadinProdRunMvnDeps`:: Runtime-only dependencies of the production build and
distribution, empty by default; see above.
`vaadinDevBuildToolsDir`:: Vaadin's build folder (Maven: `target`) for
development mode, holding the dev bundle and the dev server's files. It is a
persistent task folder of the module; the production build uses a build folder
in its own task folder.
`vaadinApplicationIdentifier`:: Identifier of the frontend bundle, `app-<artifactName>`
by default.

== Requirements

* Vaadin Flow in the version the plugin is compiled against
  (`mill.contrib.vaadin.BuildInfo.flowPluginBaseVersion`) or newer; the build
  fails with a clear message otherwise. The frontend build uses the
  `flow-plugin-base` version matching the Flow version on the application's
  classpath, loaded in an isolated worker classloader.
* Mill running on JDK 21 or newer (`mill-jvm-version`), as required by Vaadin's
  build tooling.
* Node.js is downloaded by Vaadin into `~/.vaadin` if no suitable version is
  installed.
